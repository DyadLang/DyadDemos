# DrivelineSciML: Dyad 3.5 upgrade validation

Current Julia distribution: **dyad-3.5.0**; Dyad CLI target: **3.5.1**. Forward-looking reproduction commands use the 3.5.0 Julia channel; recorded results and compiler hashes describe the original RC2 validation and have not been rerun on 3.5.1.

Target: Dyad `3.5.0` language with runtime `dyad-3.5.0-rc2` (Julia 1.13.2).
Baseline: the original project on `dyad-3.4.0` (Julia 1.12.7).
Runs use two Julia threads and one precompile task.

**Follow-up:** [calibration validation](followup-validation.md) supersedes the
Stage 1 nonconvergence limitation below. Resolving the chirp with a 0.1 ms
maximum integration step produces successful convergence on both runtimes,
with the original tolerances, data, bounds, and optimizer budget.

## Reproduction

Instantiate this project, regenerate with the Dyad 3.5 CLI, then run the existing tests and all concrete analyses:

```sh
julia +dyad-3.5.0 --project -e 'using Pkg; Pkg.instantiate()'
dyad --version
JULIA_EXECUTABLE="julia +dyad-3.5.0" dyad compile "$PWD"
julia +dyad-3.5.0 --project scripts/fix_analysis_codegen.jl
JULIA_NUM_THREADS=2 JULIA_NUM_PRECOMPILE_TASKS=1 julia +dyad-3.5.0 --project -e 'using Pkg; Pkg.test()'
DYAD_UPGRADE_OUTPUT=/path/to/results JULIA_NUM_THREADS=2 julia +dyad-3.5.0 --project scripts/validate_upgrade.jl
```

The validation driver uses the declared simulation horizons and training budgets,
checks ODE return codes and finite state/parameter values, and writes per-analysis
metrics and state trajectories. Training output goes to the validation directory.
`DYAD_UPGRADE_ONLY` selects a comma-separated subset when retrying failed runs.

## Results

The existing test suite passes: **15/15** assertions (13 demo checks and two calibration-construction regressions). All five transient
analyses return `Success` at their full declared horizons. Both calibrations run
to completion; Stage 1 reports the same pre-existing `Infeasible` optimizer
status on both runtimes. Stage 2 reports `Success` on both runtimes.

The numerical comparisons and calibration results below were originally run
with code generated by CLI `3.5.0-rc1 (e5bac67)`, using the RC2 runtime.
`fix_analysis_codegen.jl` reproducibly corrects the compiler
issue where a parametric `DyadTimeseries` value is declared with a UnionAll type:
it uses `typeof(__local__data)` for the generated symbolic parameter annotation.
A direct analysis run exposed this failure; the regular smoke tests alone did
not cover calibration construction.

### Chained calibration and held-out validation

The existing `scripts/run_calibration.jl` and `scripts/validate.jl` both complete
on 3.5. The chained fit freezes Stage 1's Maxwell branch before fitting Stage 2:
alpha = 49.63 (truth 50, -0.74%), beta = 4.970 (truth 5, -0.60%), gamma = 0.4441
(truth 0.5, -11.19%). The fitted saturation torque is 9.99 Nm versus 10 Nm truth.
Gamma remains the least well recovered parameter in this identification problem.

On the unseen tip-in, calibrated RMSE versus truth is 0.004492 rad/s (engine
speed), 0.005614 rad/s (speed difference), and 9.129e-5 rad (twist). The linear
baseline errors are 0.5234 rad/s, 0.6543 rad/s, and 0.01073 rad, respectively:
99.1% lower RMSE for each observable. The existing plot exporter also writes
`assets/validation_tipin.png` successfully (ignored generated output).

No measurement datasets were regenerated. All seven defined analyses and the
existing tests were run; no analysis or training budget was silently omitted.
